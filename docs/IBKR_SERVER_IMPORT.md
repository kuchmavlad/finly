# Серверный журнал IBKR

18 октября 2026. Реализован журнал исходных брокерских операций, отдельно от опубликованных остатков портфелей. Локальный preview и сравнение файлов остаются доступны без отправки в облако.

Обновление приёмки: пользователь подтвердил «работает» после инструкции загрузки/подтверждения на iPhone. Основной серверный сценарий подтверждён пользователем; приведённые ниже ограничения тестирования агентом сохраняются. Повтор, пересекающийся отчёт и восстановление pending на устройстве отдельно ещё не подтверждены.

## Использование

1. Settings → Import IBKR report. Выбрать пустой портфель (создать через Manage portfolios при необходимости).
2. Choose Activity Flex XML → месячный XML. Сам выбор файла ничего не отправляет.
3. Check on server **отправляет и сохраняет исходный XML** в приватной базе Finly. Сервер повторно разбирает файл, проверяет cash и сравнивает операции с журналом. Показаны new/unchanged/changed, ошибки, исходные валюты и страницы операций по 25.
4. Confirm and save to IBKR journal записывает операции и их денежные проводки одной транзакцией. Ready — готов к журналу, а не подтверждение полной истории или позиций. Blocked — весь пакет неприменим.
5. Повторить месячный XML: прежний applied-пакет, без дополнительных операций. Короткий пересекающийся отчёт: после месячного ожидается new 0 / unchanged 7 / changed 0 для проверенной пары. После подтверждения создаются только связи с новым источником, не повторные проводки.
6. После перезапуска Refresh saved reports показывает последние 20 пакетов. Старый пакет можно получить повторным выбором того же XML. При незавершённом подтверждении — Check status and retry confirmation; новые подтверждения заблокированы до разрешения pending.

Портфель связывается с одним брокерским счётом при первом применении. Ручные операции в нём запрещены; попытка возвращает понятный отказ и очищает отвергнутый manual pending. Портфель с уже записанными ручными деньгами не принимается, чтобы не задвоить пополнения. Существующие ручные операции других портфелей не меняются.

Overview и Activity по-прежнему показывают ручной учёт. Журнал IBKR читается отдельно; начальный cash из отчёта не превращается в deposit. История, начальные позиции, стоимость активов и доходность не объявляются проверенными.

## Сервер и хранение

- Edge Function `ibkr-import` принимает POST application/xml с bearer-сессией и x-portfolio-id. Auth.getUser проверяет пользователя **до чтения тела**. Gateway verify_jwt=false выбран из-за современной системы ключей; собственная проверка JWT обязательна. Service role находится только в окружении Edge Function.
- Парсер общий для Expo, Node и Deno: `supabase/functions/_shared/ibkr`. Версия адаптера в базе — flex-journal-v1. Источник истины — повторный серверный разбор; клиентские owner, нормализованные события или флаг «проверено» не принимаются.
- Источник и snapshot хранятся в `ibkr_private.reports` одной DB-транзакцией. Это осознанное упрощение первоначального Storage-плана: нет промежутка между загрузкой объекта и записью пакета. Старые `public.import_batches` и bucket `ibkr-reports` остаются резервом и не используются этим API. Новых прав на Storage нет.
- SHA-256 вычисляется Postgres по полученному UTF-8 XML; это хэш переданного текста, не обещание байтовой идентичности исходному файлу другой кодировки. Ограничения: 10 MiB, UTF-8, глубина 8, 20 000 XML-узлов, 5 000 событий для сервера; 30 секунд чтения/парсинга; 100 отчётов или 100 MiB исходных XML на пользователя. Нет автоматического удаления источников. При лимите требуется административный пересмотр хранения.
- Таблицы accounts/reports/events/postings/provenance/confirmations в закрытой схеме, RLS включён, прямые grants отсутствуют. Чтение/подтверждение — только authenticated RPC с auth.uid(); stage RPC — только service_role после Auth.getUser. SECURITY DEFINER нужен для доступа к закрытой схеме, search_path пустой, PUBLIC/anon EXECUTE отозван.
- Все decimal в JSON — строки; денежные postings в Postgres — numeric с пределом 18 целых / 18 дробных знаков. Чтение возвращает строки. Исходные атрибуты событий сохранены в signature и XML, комиссии/FX не округляются.
- Owner advisory lock совпадает с manual RPC. Он сериализует staging/confirm/manual; ключ события — owner/account/SHA-256 подтверждённой identity, с проверкой исходного ключа и signature. Перекрытие добавляет provenance. Changed, unsupported и duplicate IDs блокируют пакет; отсутствующая запись не означает отмену.
- Digest связывает hash, портфель, счёт, версию, ревизию журнала и snapshot. После применения другого пакета нужен новый server check; прежний digest получает PREVIEW_STALE. Applied-пакет неизменяем, повтор возвращает прежний результат.
- Pending содержит только reportId/digest/requestId в хранилище текущего проекта/пользователя. Сначала сохранение intent, затем статус/confirm. Timeout не равен отказу. После перезапуска статус applied позволяет очистить pending без второй записи. Смена пользователя/уход подавляет запоздалые результаты. Native pending — SecureStore, web pending — память, как и остальные записи приложения.
- Удаление Auth-пользователя каскадно удаляет его журнал. Произвольное удаление/редактирование импортированных событий через клиент не доступно.

## Развёртывание и проверки

В проект `jntgwwcgyzhgjhatozld` применены `20261018084534_ibkr_journal.sql` и `20261018084801_ibkr_owner_cleanup.sql`, Edge Function развёрнута через MCP с закреплёнными supabase-js 2.117.3 / saxes 6.0.0 и Deno lock. CLI миграции первоначально созданы штатной командой, затем имена синхронизированы с облачной историей. Повторно применять их в этой среде не нужно.

**Резервная копия не создавалась:** 18 октября пользователь явно поручил «давай без копии». Это исключение для текущего запуска отменяет прежний backup gate из плана и SUPABASE_SETUP; не является заявлением о наличии backup или проверенного восстановления. CLI не авторизован, Docker/Podman отсутствует. Платные средства не подключались.

Проверки: TypeScript, lint, Node-тесты, Deno check, iOS/Hermes и web export. SQL-тесты на PGlite проверяют идемпотентность, overlap, точность, owner isolation, grants, stale digest, ошибку посередине apply с полным откатом, manual conflict и каскадное удаление. Тесты confirmation покрывают двойное нажатие, lost reply/restart, ошибки SecureStore, смену пользователя и definitive rejection. HTTP handler отдельно проверяет auth до чтения, лимиты, повторный разбор и отсутствие исходных значений в ошибках. Все unit XML явно синтетические.

Облачный `scripts/ibkr-cloud-smoke.ts` генерирует SQL с синтетическими данными: stage/confirm/retry, precise posting, чужой owner, прямой доступ, anon. Весь сценарий BEGIN/ROLLBACK; тестовые записи не сохраняются. Проверен HTTP 401 развёрнутой функции без JWT. Реальная пара XML повторно проверена **локально**: 11/7 событий, cash сходится, 7 unchanged. Пользовательские файлы агентом в облако не отправлялись.

Ограничения проверки: SQL SET ROLE не заменяет две настоящие Auth-сессии через REST; полноценный вход/загрузка через Edge Function и новый UI на физическом iPhone ещё требуют приёмки. PGlite выполняет запросы последовательно: независимые параллельные сетевые транзакции не воспроизводились. Защита конкуренции обеспечена DB lock и уникальными ограничениями, но отдельный нагрузочный тест не заявляется.

Security Advisor: ожидаемые INFO для закрытых RLS-таблиц без политик ([пояснение](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy)), WARN для намеренно доступных authenticated SECURITY DEFINER RPC ([пояснение](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable)). Прежнее предупреждение об отключённой [leaked password protection](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection) осталось, настройки Auth не менялись. Нет обещания, что Advisor без замечаний.
