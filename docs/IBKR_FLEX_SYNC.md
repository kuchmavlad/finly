# IBKR Flex: получение отчётов и отдельное подтверждение

18 октября 2026. Реализован ручной запуск; реальное получение из IBKR ещё не проверено. Токены и пользовательские XML агентом не запрашивались и не использовались. Holdings/Overview/доходность не входят в этот этап.

## Настройка на iPhone

1. Открыть обновлённое приложение → Settings → Sync IBKR reports. Нужен портфель, уже связанный с IBKR подтверждённым XML-импортом. Ранее проверенный портфель подходит, повторный импорт для настройки не нужен.
2. В IBKR Client Portal → Performance & Reports → Flex Queries найти **существующий проверенный Activity Flex Query**. Оставить XML, один счёт и прежний набор полей/секций, включая Transaction ID и Cash Transfer. Скопировать его Query ID. Trade Confirmation не подходит.
3. В Flex Web Service Configuration включить сервис и Generate New Token. Выбрать подходящий срок в Should Expire After: по документации значение по умолчанию — лишь 6 часов. Новый токен инвалидирует предыдущий. Для текущего Supabase Edge нет настроенного фиксированного исходящего IP; привязка к IP телефона не подойдёт. Если нужен IP allowlist, сначала потребуется отдельное решение для исходящего адреса; платные услуги не подключать.
4. **Токен вводить только в поле Flex token в Finly, не в чат, SQL Editor, Git или .env.** Выбрать связанный портфель, ввести Query ID и токен → Save encrypted connection. Поле токена очищается; сервер не возвращает его значение. Замена подключения выключает ежедневный режим и требует новой ручной проверки.
5. Sync now. Запрашиваются семь завершённых календарных дней относительно UTC: `fd = UTC today − 7`, `td = UTC today − 1`. Отображается запрошенный период. Подождать генерацию; при выходе/перезапуске вернуться и нажать Resume sync. После сетевой ошибки Refresh status восстанавливает серверное состояние. Текущий день не запрашивается.
6. Review report and confirm import → проверить период, портфель, new/unchanged/changed, ошибки и cash → отдельно **Confirm and save to IBKR journal**. Скачивание само по себе операций не применяет. Blocked нельзя подтвердить. Если другой импорт изменил журнал, Recheck saved report обновит сравнение исходного сохранённого XML без запроса к IBKR; затем снова требуется подтверждение.
7. Повторить Sync now / подтверждение, проверить отсутствие дублей. Успешный запрос повторно используется в течение 10 минут. Проверить уход со страницы, возврат и восстановление ожидания. Сообщить результат без токена и финансовых данных. Для проверки истечения можно заменить токен после его отзыва в Portal; это инвалидирует старый токен и для других использующих его программ.

Disconnect and delete stored token удаляет подключение, секрет и выключает ежедневный режим. Сохранённые отчёты и журнал остаются. Это не отзывает токен в IBKR: при необходимости отозвать/заменить его в Portal.

## Ограничения IBKR, проверенные 18 октября

- [Flex Queries](https://www.ibkrguides.com/clientportal/performanceandstatements/flex.htm): текущий календарный год и четыре предыдущих. В 2026 ожидаемое окно начинается с 2022 года, но фактическая доступность конкретного счёта и полнота истории этим не доказаны.
- [Конфигурация Web Service](https://www.ibkrguides.com/clientportal/performanceandstatements/flex3.htm): диапазон одного запроса до 365 дней, даты `yyyymmdd`, User-Agent обязателен. Наша синхронизация использует только последние 7 завершённых дней; автоматический backfill всей истории не реализован.
- [SendRequest](https://www.interactivebrokers.com/docs/web-api/api-reference/send-request) → ReferenceCode → [GetStatement](https://www.interactivebrokers.com/docs/web-api/api-reference/get-statement). `q` сначала Query ID, затем ReferenceCode. [Новая инструкция](https://www.interactivebrokers.com/docs/web-api/flex-web-service/using-flex-web-service/generate-the-report) предписывает игнорировать URL в ответе. Оба адреса в коде фиксированы, redirects запрещены.
- [Коды и лимиты](https://www.ibkrguides.com/clientportal/performanceandstatements/flex3error.htm): 1 запрос/секунду и 10/минуту на токен. 1019 — ожидание, 1018 — rate limit; 1012/1015 — токен; 1013 — IP; 1014 — Query ID. Отсутствие отчёта не означает отсутствие операций.

## Серверная модель

- `ibkr-flex` проверяет Auth.getUser **до чтения тела**. Ввод — ограниченный JSON до 2 KiB по HTTPS. Публичный ответ содержит только `ok` или разрешённый код. Токен кратковременно находится в памяти формы/запроса; не записывается на устройство, в EXPO_PUBLIC, сборку, логи или исходники. Поле очищается при submit, потере фокуса маршрута и переходе приложения в фон. Не добавлять body/URL tracing к этому endpoint.
- Секрет зашифрован в [Supabase Vault](https://supabase.com/docs/guides/database/vault). В закрытой `ibkr_private.flex_connections` — ссылка на секрет и SHA-256 для запрета общего токена у разных владельцев. Клиенты не имеют grants на эти таблицы/Vault; RLS включён. Только service_role RPC отдаёт credential серверному worker. Администраторы проекта с доступом к Vault по-прежнему являются доверенными.
- При обследовании облака: SQL `log_statement=ddl`, duration logging выключен, параметры ошибок не логируются, pgaudit параметров выключен. Приложение не логирует входные тела, XML, полные IBKR URL, токены или исключения транспорта. Не включать логирование bind-параметров/тел запросов при эксплуатации.
- Один сохранённый run на владельца, DB owner lock, lease 90 секунд, UUID fencing. Между запросами минимум 10 секунд; rate limit откладывает повтор на 120 секунд, другие временные ошибки — backoff до 300 секунд. До 12 попыток и 30 минут. Потерянный ответ GetStatement повторяет тот же reference. Потерянный SendRequest может повторно сгенерировать **отчёт**, но не применяет операции. Посторонние программы с тем же токеном не управляются нашей очередью.
- ReferenceCode и период сохраняются на сервере. Прерванный worker освобождается по истечении lease; запоздалый worker не может записать результат после замены подключения. Во время активного lease замена настроек отклоняется. Токен может быть удалён сразу; поздняя запись после disconnect отклоняется.
- XML повторно разбирается общим строгим parser; счёт должен совпасть с уже подтверждённой связью портфеля, период — точно с запросом. Несовпадение блокирует staging; полнота истории не предполагается. Сохраняются прежние лимиты parser, исходные валюты, decimal strings, numeric precision и проверки unsupported/changed.
- `finish_ibkr_flex` атомарно передаёт XML/snapshot в **существующий `stage_ibkr_report`** и сохраняет статус синхронизации. Операций в журнале при этом нет. `confirm_ibkr_report`, digest/revision и сохранённый pending остаются прежними. `recheck_ibkr_report` работает только с собственным доверенным сохранённым источником, не принимает новый snapshot от клиента.
- `lastReceivedAt` — XML сохранён, даже если blocked. `lastSuccessAt` — последняя успешная загрузка и проверка ready/applied; это **не дата применения операций**. Applied timestamp показан в журнале. Последняя успешная дата не исчезает из-за временной ошибки нового запуска.
- Хранилище сохраняет прежний предел 100 отчётов / 100 MiB на пользователя. Ежедневный режим может исчерпать его примерно за 100 разных отчётов либо раньше по размеру. Автоудаления нет: STORAGE_LIMIT требует отдельного решения по хранению, без потери исходников.

## Ежедневное получение — подготовлено, пока выключено

Worker `ibkr-flex-worker` использует отдельный секрет планировщика, а не токен пользователя или service_role в cron. Подготовлен `scripts/enable-ibkr-flex-schedule.sql`; **он не применён**, pg_cron/pg_net в этой задаче не включались. Реальный ручной сценарий должен быть проверен первым.

После успешного ручного получения и приёмки:

1. Администратор проверяет manualVerified и развёрнутый worker, затем выполняет подготовленный SQL в том же проекте. Скрипт проверяет наличие успешного ручного запуска, генерирует scheduler secret внутри Vault без вывода значения, устанавливает pg_cron/pg_net и dispatcher. Токен брокера в SQL не вводится.
2. В Finly Refresh status → Enable daily retrieval at 07:00 UTC. До готовности dispatcher и ручной проверки кнопка не показывается; RPC также проверяет оба условия. Выключение доступно там же.
3. Dispatcher проверяет due-задания каждую минуту и отправляет до пяти вызовов. Новый диапазон запрашивается один раз за UTC-день после 07:00, затем продолжается ожидание текущего run. Это старт окна, не гарантия готовности данных IBKR. Lease/nextAttemptAt ограничивают повторные сетевые вызовы.
4. **Без пользователя**: запрос → ожидание → получение → проверка → приватное сохранение XML и preview. **С участием пользователя**: просмотр и подтверждение каждого пакета. Никакого вызова confirm в worker или расписании нет. Ошибки токена/IP/query выключают ежедневный режим. Результат виден при следующем открытии Finly; push/email-уведомлений нет.
5. После простоя более семи дней автоматический запуск не восстанавливает пропущенный период. Нужны отдельные XML-импорты и проверка покрытия; отсутствие истории не маскируется. Суточные отчёты с перекрытием используют существующую дедупликацию; исчезнувшие строки не считаются отменами.

Отключение инфраструктуры: `select cron.unschedule('finly-flex-dispatch');` и отключить daily для подключений. Финансовый журнал не удалять. Планировщик использует бесплатные доступные компоненты проекта, но их квоты не бесконечны; тариф и платные услуги не менялись.
