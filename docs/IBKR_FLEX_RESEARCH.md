# IBKR Flex и архивная история

Исследование: 15 октября 2026. Статус: документация проверена, доступность на конкретном счёте и реальные файлы **не проверены**. Подключение счёта, сервер и финансовые расчёты не реализованы.

## Вывод

Activity Flex XML подходит как кандидат для ежедневного серверного импорта и начальной загрузки доступной истории. Trade Confirmation недостаточно для полного учёта денежных потоков. Архивные Activity Statements нужны как резервный источник и средство сверки. Это техническое предложение; полноту данных подтвердит отдельная проверка файлов.

По [правилам Flex](https://www.ibkrguides.com/clientportal/performanceandstatements/flex.htm) доступны четыре предыдущих календарных года и текущий год. Следовательно, на дату исследования ожидаемое окно — с 2022-01-01 по доступную дату 2026 года, включая 2023. Это вывод из политики хранения, а не гарантия наличия всех операций конкретного счёта.

## Глубина истории

| Источник | Документированное окно | Применение |
| --- | --- | --- |
| Activity Flex | Четыре предыдущих календарных года + текущий | Основной первоначальный импорт и ежедневные обновления |
| Daily / Custom Date Range Activity Statements | Четыре предыдущих календарных года + текущий | Контроль и резерв |
| Monthly Activity Statements | Предыдущие 60 месяцев | Архив по месяцам |
| Annual Activity Statements | Пять предыдущих лет | В 2026 году ожидаются 2021–2025; проверить в Portal |
| Более старые отчёты | Возможен запрос за плату | Не заказывать в рамках нулевого бюджета |

Источник архивной политики: [Client Portal — Statements](https://www.ibkrguides.com/clientportal/performanceandstatements/statements.htm). Старые инструкции EmployeeTrack содержат другие сроки; для этого проекта ориентируемся на текущую инструкцию Client Portal. Не обещаем семь лет доступности.

Если начало счёта раньше доступного окна, сначала использовать уже сохранённые пользователем отчёты. При отсутствии ранних операций можно зафиксировать подтверждённые начальные остатки и ограниченную дату начала учёта. Это не полная история: доходность с открытия и исходная себестоимость остаются неизвестными. Остаток на начало периода не превращать в выдуманное пополнение.

## Протокол будущего сервера

По [API SendRequest](https://www.interactivebrokers.com/docs/web-api/api-reference/send-request) и [GetStatement](https://www.interactivebrokers.com/docs/web-api/api-reference/get-statement):

1. GET `https://ndcdyn.interactivebrokers.com/AccountManagement/FlexWebService/SendRequest`: `t` — токен, `q` — ID шаблона, `v=3`.
2. Для истории передавать `fd` и `td` вместе; альтернативно `p` — количество последних дней. Не смешивать эти способы.
3. Проверить XML `Status`, получить `ReferenceCode`.
4. GET на том же хосте и пути `/GetStatement`: `q` теперь содержит ReferenceCode, вместе с `t` и `v=3`.
5. Проверить, что получен именно отчёт нужного счёта/периода, а не XML с ошибкой при HTTP 200.

[Инструкция конфигурации](https://www.ibkrguides.com/clientportal/performanceandstatements/flex3.htm) ограничивает диапазон 365 днями, задаёт формат `yyyymmdd` и требует User-Agent. Предлагаем первоначальную загрузку по месяцам: так високосный 2024 год не создаст запрос на 366 дней. Границы и фактические даты в ответе сверять; пропущенный диапазон не считать импортированным.

В новой [инструкции генерации](https://www.interactivebrokers.com/docs/web-api/flex-web-service/using-flex-web-service/generate-the-report) сказано игнорировать URL из ответа. Использовать фиксированный endpoint выше. На этой странице есть несогласованность: текст упоминает `q` для периода, пример использует `p`; следуем справочнику API, где `q` — Query ID, `p` — период.

Токен создаётся в Portal, поддерживает ограничение IP; генерация нового инвалидирует текущий. Хранить только в серверном secret storage, не в Expo, `EXPO_PUBLIC_*`, Git, чате или логах. Поскольку токен находится в query string, исключать полный URL из HTTP/APM/proxy-логов и ошибок. Исходные отчёты также содержат персональные финансовые данные: отдельное закрытое хранилище, не репозиторий.

## Повторы и ежедневный импорт — проектное предложение

- Один серверный запуск в сутки, независимо от приложения. Время выбрать после проверки фактической готовности отчёта; часовой пояс расписания задавать явно. Не обещать данные текущего дня сразу после сделки.
- Запрашивать последние 7 календарных дней с перекрытием; ежемесячно пересверять более широкий период. Число 7 — наше исходное предложение, не гарантия срока исправлений IBKR.
- Общая очередь на токен: консервативно не чаще одного запроса за 10 секунд для обоих endpoints, без параллельных задач на тот же токен. Документированные ограничения — 1 запрос/секунду и 10/минуту.
- `1019` означает генерацию; повторять GetStatement с тем же ReferenceCode. `1018` — ограничение частоты. Для временных ошибок (`1001`, `1004`–`1009`, `1021`) — ограниченный backoff, затем перенос запуска. Предложение: до 8 попыток, задержки 10/20/40/80/160/300/300 секунд с положительным jitter.
- `1012`/`1015` требуют обновления/проверки токена; `1013` — IP; `1014` — шаблона. Не повторять их бесконечно. `1003` не означает отсутствие операций; `1017` не даёт права пометить диапазон успешным.
- Ошибки сети, некорректный XML, неожиданный счёт/диапазон или неизвестный тип операции оставляют пакет на проверке. Последние корректные данные сохраняются с датой актуальности.

Коды и лимиты: [Flex v3 errors](https://www.ibkrguides.com/clientportal/performanceandstatements/flex3error.htm). Политика очереди, повтора и перекрытия выше — решения Finly, ещё не проверенные нагрузкой.

## Состав пробного Activity Flex XML

Список секций основан на [Activity Flex Query Reference](https://www.ibkrguides.com/reportingreference/reportguide/activity%20flex%20query%20reference.htm). Точные XML-атрибуты и их присутствие фиксировать по образцу, не угадывать по названиям полей интерфейса.

| Секции | Зачем Finly |
| --- | --- |
| Account Information, Financial Instrument Information | Счёт, базовая валюта, Conid/ISIN, описание инструмента |
| Trades, уровень Executions | Сделки; не складывать исполнения с Orders, Summary и Closed Lots |
| Cash Transactions | Пополнения, выводы и выплаты с исходной валютой и типом |
| Transfers, Corporate Actions | Переводы активов, изменения инструментов, погашения; не подменять покупкой/продажей автоматически |
| Cash Report, Open Positions, Net Asset Value | Контроль остатков и оценки на конец периода |
| Change in NAV, Currency Conversion Rate | Дополнительная сверка изменений и брокерских курсов |
| Interest Accruals, Change in Dividend Accruals, Transaction Fees | Отделение начислений, выплат и расходов |

В [Trades](https://www.ibkrguides.com/reportingreference/reportguide/tradesfq.htm) выбрать идентификаторы сделки/исполнения и исходной отменённой сделки, даты сделки/расчёта, валюту, инструмент, количество, цену, multiplier, proceeds, commission с валютой, taxes, net cash и коды. Некоторые order-поля доступны только в однодневных отчётах: не делать их обязательным ключом архивного импорта.

[Cash Transactions](https://www.ibkrguides.com/reportingreference/reportguide/cash%20transactionsfq.htm) содержит валюту, сумму, дату, тип и привязку к инструменту/сделке. Наличие устойчивого ID каждой денежной записи необходимо проверить на XML; не предполагать его универсальность.

Отдельная проверка облигаций обязательна: единица quantity (номинал или штуки), multiplier, clean/dirty price, НКД, купон, погашение и частичное погашение. Demo-модель с целым количеством не является готовым адаптером IBKR. Нельзя повторно вычесть комиссию, уже включённую в net cash, либо посчитать начисление и последующую выплату двумя доходами. FX-сделка должна сохранять обе валютные стороны; налог и дивиденд — отдельные записи.

## Целостность и архивный импорт — проектное предложение

Сначала сохранять пакет источника (тип, версия шаблона/парсера, счёт, запрошенный и фактический период, время генерации/получения, hash файла). Затем парсить в staging и сверять; только после успешной проверки публиковать атомарно. XML-парсер должен запрещать DTD/внешние сущности, ограничивать размер и глубину.

Для событий использовать ключ источника + счёт + вид записи + устойчивый ID, если он действительно есть. Один ID с изменившимся содержимым — новая ревизия, а не ещё одна операция. Hash файла устраняет лишь повтор того же файла, не дубли перекрывающихся отчётов. При отсутствии ID составной fingerprint — только кандидат: одинаковые легитимные платежи нельзя молча склеивать. Неоднозначности направлять на проверку.

Ручные исправления хранить отдельным слоем с аудитом. Новый импорт обновляет исходник, а конфликт с исправлением показывает пользователю. Удаление импортированного события — сохраняемое исключение с причиной; отмена брокером — отдельная ревизия/связь. Исчезновение строки из нового отчёта само по себе не означает отмену.

Архивный CSV Activity Statement и Flex XML требуют разных адаптеров. PDF использовать для визуальной сверки; автоматический разбор PDF не включать в первый импорт. При перекрытии архива с Flex выбирать подтверждённый источник периода либо сверять записи, не суммировать оба набора. Сопоставление старых и новых account ID при переносе счёта требует подтверждения, а не догадки.

Денежные значения, количества, цены и FX читать как десятичные строки с сохранением точности; не округлять сразу до cents и не пропускать через JS Number. Хранить trade date и settlement date раздельно, исходный часовой пояс/формат — явно. Пропущенные поля не заменять нулями.

Ежедневные NAV и оценки на даты потоков проверять отдельно: годовой отчёт не доказывает наличие ежедневного ряда. Flex не закрывает выбор источника актуальных котировок, USD/UAH, S&P 500 TR или методики TWR/XIRR.

Документальное исследование завершено. Критерий следующего этапа — подтверждённая карта покрытия истории и набор примеров для парсера, а не только успешная выдача одного XML. До этого реальный импорт и доходность с открытия нельзя считать проверенными.
