# Проверка первых пользовательских Flex XML

16 октября 2026. Получены два реальных пользовательских файла вне репозитория: месячный Activity Flex XML и XML за вложенный диапазон. Проверены локально, без загрузки в облако. Здесь только структурные выводы: исходники, номера счетов, IDs операций и финансовые значения не публикуются. Это исследовательская проверка, не production-парсер и не подтверждение полной истории.

## Актуально: выгрузка после включения Transaction ID в Cash Transactions

В последней паре CashTransaction.transactionID заполнен у всех денежных записей, уникален внутри каждого файла и совпадает у общей записи на пересечении. Все атрибуты этой записи идентичны; levelOfDetail = DETAIL. tradeID и actionID пустые — их нельзя использовать как обязательный ключ пополнения. Сохраняется точное равенство событий изменению cash по каждой исходной валюте обоих периодов, включая Transfer.cashTransfer. Перекрывающиеся сделки и перевод также идентичны.

Для наблюдаемого типа денежных операций можно проектировать identity как owner + broker account + record kind + transactionID. Проверка этой пары не доказывает уникальность ID для всех типов, исправлений и всей истории; неоднозначные/пустые ID по-прежнему блокируют автоматическое применение. Появились также reportDate, settleDate, availableForTradingDate, exDate, actionID и levelOfDetail. В файлах есть deliveryType, но нет dividendType; назначение полей дивидендов ещё не подтверждено реальной выплатой. Дополнительная выгрузка этих же периодов для начала read-only preview не нужна.

Ниже сохранены исторические результаты ранних версий шаблона. Отметки об отсутствии суммы перевода и transactionID больше не относятся к последней паре. Реальные файлы не копировались в проект; проверки выполнялись локально с Decimal, production-код не изменён.

## Повторная выгрузка после уточнения Transfers

Пользователь прислал обновлённую пару за те же периоды. Поле `cashTransfer` теперь присутствует и содержит сумму денежного перевода; также добавлены dateTime, settleDate и levelOfDetail (`TRANSFER`). С учётом cashTransfer сверка событий с изменением cash по каждой исходной валюте сходится точно в обоих файлах. Все сделки и перевод короткого периода по-прежнему полностью совпадают с месячным; денежная запись тоже совпадает. Ограничение суммы перевода, описанное ниже для первой версии, снято для этих образцов. Направление OUT и иные виды переводов ещё не проверены.

CashTransaction по-прежнему не содержит transactionID, а tradeID пустой. Следующий запрос — полный список полей Cash Transactions, чтобы проверить наличие отдельного идентификатора в интерфейсе. Универсальная дедупликация cash, исправления, полнота истории и сверка начальных позиций остаются неподтверждёнными; точная сверка cash не означает готовность импорта к применению.

## Подтверждено на первоначальных образцах

- XML корректно читаются; корень `FlexQueryResponse`, один `FlexStatements/FlexStatement` в каждом. Счёт совпадает между файлами и всеми содержащими accountId записями. Периоды берутся из fromDate/toDate, а не имени файла; атрибут period пустой.
- `Trades/Trade`: уровень `EXECUTION`; tradeID и ibExecID заполнены и уникальны внутри каждого файла. Все исполнения короткого периода имеют идентичные атрибуты в месячном. Это подтверждение только для этой пары файлов, не гарантия глобальной уникальности или поведения исправлений.
- `CashTransactions/CashTransaction`: amount, currency, dateTime, type, code и инструментальные поля. Отдельного transactionID нет, tradeID пустой. Запись на пересечении совпадает полностью. Fingerprint остаётся кандидатом сопоставления: идентичные легитимные платежи нельзя молча склеивать.
- `Transfers/Transfer`: transactionID заполнен и стабилен на пересечении. В образце денежного INTERNAL-перевода quantity, transferPrice, positionAmount и positionAmountInBase нулевые, отдельного cash amount нет. Cash Report содержит ненулевой accountTransfers, равный необъяснённому остатку сверки событий. Нельзя восстанавливать отдельную проводку из агрегата без подтверждения источника суммы. Нужен просмотр доступных полей Transfers и/или контрольный Activity Statement.
- `OpenPositions/OpenPosition`: уровень `SUMMARY`; количество называется position, а не quantity. `SecuritiesInfo/SecurityInfo` содержит описание инструментов. AccountInformation.currency задаёт базовую валюту.
- `EquitySummaryInBase/EquitySummaryByReportDateInBase`: несколько дат, включая дату перед началом каждого диапазона; значения на общих датах совпадают. Это ещё не доказательство непрерывного календарного ряда для доходности.
- Cash Report включает `BASE_SUMMARY` и отдельные валютные строки, а также поля с суффиксами Sec/Com. Их нельзя суммировать повторно с итоговыми полями.

## Сверка точными decimal

Проверка выполнена Python Decimal с precision 100, без преобразования сумм в float.

- Для STK в этих образцах netCash = proceeds + taxes + ibCommission. Для CASH это равенство не выполняется: netCash нулевой при ненулевых quantity/proceeds и коде AFx. В FX необходимо сохранять обе валютные стороны; нельзя использовать netCash как универсальное движение денег.
- Кандидат FX mapping для наблюдаемой валютной пары: quantity в первой валюте symbol, proceeds во второй, комиссия в ibCommissionCurrency. Это подтверждено сверкой образцов, но не расширяется автоматически на другие типы FX, корректировки и инструменты.
- Сумма компонентов Cash Report сходится точно с endingCash - startingCash для исходных валют обоих файлов. В BASE_SUMMARY есть малые ненулевые остатки на уровне десятичных разрядов отчёта; причина и допуск не утверждены, автоматически их не скрывать.
- Сверка событий с cash сходится для одной валюты; в другой остаётся расхождение, равное accountTransfers. Нулевая сумма в Transfer не позволяет закрыть его на уровне событий. Применение в ledger остаётся заблокированным.

## Чего эти образцы не подтверждают

TransactionTaxes, CorporateActions, InterestAccruals и ChangeInDividendAccruals присутствуют как пустые секции. Их реальные атрибуты и обработка не проверены. Нет примеров отмен/исправлений, выплат/удержаний, облигаций или дробного количества акций. Отдельной секции Currency Conversion Rate нет; fxRateToBase присутствует у событий. Полная история с открытия, архивы и 2023 год не проверены. Позиции пока не сверялись от начального снимка.

Следующий шаг: уточнить поле суммы денежного перевода и наличие transaction ID для cash в интерфейсе, получить исправленную пару XML либо дополнительный контрольный источник.
