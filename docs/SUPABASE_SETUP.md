## Что уже подготовлено

- `.env.local` содержит URL и publishable key пользователя и исключён из Git. `.env.example` — шаблон для другого компьютера. Это публичные клиентские параметры; они не заменяют авторизацию и RLS.
- Стартовый экран: вход email/password. Settings → Open account: создание портфелей, запись пополнений/выводов, просмотр последних 100 денежных операций и выход.
- На iOS/Android сессия и ожидающий подтверждения запрос хранятся через SecureStore. На web-превью — только в памяти до перезагрузки. Ошибка защищённого хранилища не переключает приложение на открытое хранение. Большие payload сессии могут быть отклонены платформой; этот случай требует проверки на устройстве.
- SQL создаёт таблицы `portfolios`, `cash_entries`, `cash_entry_audit`, `import_batches`, три RPC и закрытый bucket `ibkr-reports`. Клиент не может напрямую менять/удалять финансовые записи или аудит. Изменения пока не поддерживаются.
- Исходные отчёты в будущем будут храниться в `ibkr-reports/<user UUID>/...`. Загрузка файлов пока закрыта политиками; парсер и подтверждение импорта ещё не реализованы.
- Инвестиционные инструменты, котировки, сделки, финансовая аналитика и планировщик IBKR — следующий этап, а не часть этой минимальной миграции. Demo-вкладки не используют серверные записи.

## Выполнить в панели Supabase

1. Открыть [проект](https://supabase.com/dashboard/project/jntgwwcgyzhgjhatozld). Проверить Free-план и выбранный регион в настройках. Регион и биллинг через публичный ключ не проверялись.
2. Authentication → Sign In / Providers: оставить **Allow new users to sign up** и email/password включёнными. Пользователь запросил регистрацию в приложении. Проверено 15 октября: disable_signup=false, mailer_autoconfirm=false — требуется подтверждение email.
3. Для текущего проекта пропустить: миграция уже применена через MCP. Для новой пустой среды применить `supabase/migrations/20261015065115_pilot.sql` один раз.
4. Authentication → Users → Add user → Create new user: создать личный пилотный аккаунт с email и отдельным сильным паролем, подтвердить email административной опцией для собственного адреса. Не использовать пароль панели Supabase или брокера. Публичная регистрация теперь включена по запросу пользователя. Создать второй отдельный аккаунт только для проверки изоляции.
5. Перезапустить Expo: `npm.cmd start -- --go --clear`. На стартовом экране войти под пилотным пользователем. Его учётная запись независима от аккаунта администратора Supabase.

Пароль базы, service_role/secret keys и пароль пользователя не присылать в чат. Публичный ключ не даёт возможности применить SQL или создать пользователей административно. Для автоматического применения в будущем нужен отдельно авторизованный административный доступ; не добавлять его в Expo.

## Проверка после применения

1. Создать `Test portfolio`, записать пополнение `100.123456789012345678 USD` на прошедшую дату. Проверить точное отображение суммы. Это настоящая сохранённая тестовая запись; использовать только тестовый портфель/аккаунт.
2. Перезапустить приложение, войти при необходимости: запись должна остаться. Повтор создания портфеля с тем же именем возвращает существующий портфель.
3. Записать вывод `10 USD`; проверить отказ вывода сверх записанного остатка, в другой валюте без остатка и на будущую дату. Сервер проверяет дневные остатки, включая будущие относительно задней даты записи. Внутридневная последовательность пока не моделируется.
4. При потере ответа повторить pending operation: должен использоваться тот же request ID. На native незавершённый запрос сохраняется и восстанавливается после перезапуска. Подтверждённая сервером ошибка валидации позволяет исправить форму. После переустановки сохранность pending не гарантируется — сверить последние записи до повторного ввода.
5. Выйти и войти вторым пользователем: портфели и операции первого не должны появиться. Проверить прямые API-запросы с JWT второго пользователя, включая чужой portfolio ID. Тесты PGlite проверяют SQL, но не заменяют проверку развёрнутого проекта.
6. Проверить native-сессию на iPhone после перезапуска, работу при сворачивании/возврате, отсутствие старых записей после смены аккаунта, клавиатуру и VoiceOver. Web-превью намеренно не сохраняет сессию между перезагрузками.

## Ограничения первого подключения

Реальный импорт пока отсутствует. Валюта cash-записи — трёхбуквенный код; справочник валют и проверка minor units ещё не подключены. Значения передаются в SQL строками, хранятся в `numeric`, возвращаются строками. Нет конвертации в USD/UAH и настоящей доходности. Отрицательный cash/margin не поддерживается. Для сверки используются даты UTC сервера; дата операции вводится явно.

Финансовые записи пилота неизменяемы через клиент. Исправления, обратные операции, удаление аккаунта, экспорт через UI, почтовое восстановление и приглашения ещё не реализованы. Для восстановления доступа пилотный владелец использует административные инструменты; перед внешними пользователями нужен полноценный процесс восстановления.

## Резервные копии и дальнейшее развитие

На Free нельзя рассчитывать на включённые автоматические backups. Перед реальным импортом и перед миграциями нужен отдельный защищённый экспорт данных; копирование только SQL-миграций не сохраняет пользовательские записи. Файлы Storage копируются отдельно от дампа базы. До проверки восстановления реальные архивы не загружать.

Следующая задача инфраструктуры: настроить ручной экспорт базы и файлов вне Git и проверить восстановление в отдельной тестовой среде. Публичного ключа для полного административного backup недостаточно. Затем — образцы IBKR, таблицы инструментов/событий, staging импорта и согласованные правила учёта. Не адаптировать реальные сделки к упрощённым demo-типам.

Источники: [Supabase Free](https://supabase.com/pricing), [backup](https://supabase.com/docs/guides/platform/backups), [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [Storage policies](https://supabase.com/docs/guides/storage/security/access-control), [Expo SecureStore SDK 57](https://docs.expo.dev/versions/v57.0.0/sdk/securestore/).

Успешный ответ без сессии показывает инструкцию подтвердить email и вернуться ко входу; при наличии сессии защищённая навигация открывает приложение. Проверены облачные настройки: email включён, signup разрешён, подтверждение обязательно. Получение письма и полный цикл регистрации нового пользователя ещё не проверены. Для внешних пользователей проверить SMTP и Site URL в Supabase: стандартная почта ограничена, а редирект после подтверждения должен вести на доступную страницу.
