## Граница первого этапа

Первый источник — вручную выгруженный Activity Flex XML. Сначала автономный разбор и предпросмотр без изменения учёта, затем серверное staging и отдельное подтверждение применения. Activity Statement CSV — отдельный будущий адаптер для архивов; PDF — контроль человеком. Автосинхронизация раз в сутки остаётся требованием следующего этапа, после проверки ручного пути. Сейчас не нужны токен Flex, подключение счёта, расписание или платные услуги.

Первый применяемый пакет должен целиком покрываться проверенными правилами адаптера. Неподдерживаемая финансовая запись блокирует весь пакет: нельзя импортировать лишь понятные строки и показать остаток как полный. Допустим частичный период истории с подтверждённым начальным снимком и явной датой начала учёта. Это не полная история с открытия. XIRR, TWR, себестоимость и инвестиционная доходность в этот этап не входят.

## Что получить от пользователя

Начать с минимального набора ниже; если периоды совпадают, повторно выгружать одинаковый файл не нужно. Выгрузка вручную в Portal не означает подключение Finly к брокеру.

| Образец | Назначение | Что проверим |
| --- | --- | --- |
| Activity Flex XML за недавний завершённый месяц с операциями | Основной адаптер | Реальные имена/типы атрибутов, вложенность, пустые секции, знаки сумм, валюты, даты, уровень Executions, IDs |
| XML за несколько дней внутри того же месяца, тем же шаблоном | Перекрытие | Стабильность IDs и содержимого одной записи между периодами; две одинаковые реальные операции не должны сливаться |
| Activity Flex XML за месяц 2023 года с активностью | Старая история | Фактическая доступность 2023, отличия структуры, идентификаторы и состав секций |
| XML за самый ранний доступный месяц | Нижняя граница | Фактический период и начальные остатки; наличие истории до первой сделки |
| Annual Activity Statement за 2023: CSV и обезличенный PDF | Независимая сверка | Годовые потоки, позиции, остатки и контроль на общей дате; CSV не считать Flex |
| Annual Activity Statement за самый ранний доступный год: CSV/PDF, плюс имеющиеся старые архивы | Покрытие до окна Flex | Разрывы, старые/закрытые/перенесённые счета; платные архивы не заказывать |
| Activity Statement за тот же недавний месяц: CSV или PDF | Сверка первого пакета | Начальный/конечный cash каждой валюты и позиции на тех же границах, что в XML |

Вместе с файлами нужны только ещё неизвестные сведения: месяц/год открытия, наличие переноса/закрытых счетов и сохранённых архивов; описание выбранных полей шаблона и форматов дат/чисел, фактически доступные в Portal годы. Номер настоящего счёта не нужен. Если отчёт недоступен, зафиксировать это, не заменять его вымышленным примером.

Для XML выбрать Account Information, Financial Instrument Information, Trades (Executions), Cash Transactions, Transfers, Corporate Actions, Cash Report, Open Positions, NAV; для дополнительных сверок — Change in NAV, Currency Conversion Rate, Interest Accruals, Change in Dividend Accruals, Transaction Fees. В сделках нужны доступные IDs/связи отмены, trade/settlement dates, instrument, quantity, multiplier, price, proceeds, commission и её валюта, taxes, net cash, codes. Названия здесь — поля интерфейса/справочника, **не утверждённые XML paths**. См. [справочник секций](https://www.ibkrguides.com/reportingreference/reportguide/activity%20flex%20query%20reference.htm), [Trades](https://www.ibkrguides.com/reportingreference/reportguide/tradesfq.htm) и [Cash Transactions](https://www.ibkrguides.com/reportingreference/reportguide/cash%20transactionsfq.htm).

Дополнительные реальные случаи запросить только если они были на счёте и отсутствуют в первом наборе: дробная сделка, FX с обеими валютными сторонами, дивиденд и удержание налога, комиссия в другой валюте, отмена/исправление сделки, перевод бумаг, корпоративное действие, два одинаковых платежа. Для облигаций нужны покупка с НКД, купон и погашение/частичное погашение: до их проверки эти случаи остаются неподдерживаемыми. Отсутствие случая в образцах не доказывает поддержку.

### Обезличивание

- Работать с копиями, оригиналы и таблицу соответствия хранить вне Git. Не присылать логин, пароль, Flex token, банковские реквизиты, адрес, телефон, email, налоговые номера или подписи.
- Заменить личные сведения и account IDs во всех секциях, именах файлов и метаданных; одному счёту соответствует один псевдоним во всех файлах, разным счетам — разные. Сохранять допустимую форму значения, когда она влияет на разбор.
- Идентификаторы операций можно псевдонимизировать, но одинаково во всём наборе, включая ссылки на исправления/отмены. Не заменять все IDs одним значением.
- Сохранить структуру, названия полей, пустые значения, коды, валюты, даты, точные количества/суммы и связи. Публичные идентификаторы инструментов полезны для проверки. Если числа или даты изменены, явно пометить файл как преобразованный: он не доказывает фактические итоги и доступность истории. Не присылать финансовые значения, которыми пользователь не готов поделиться.
- PDF редактировать с реальным удалением текста/метаданных, а не чёрным прямоугольником поверх текста; проверить поиск и копирование. Обезличенные финансовые отчёты тоже не публиковать в репозитории/PR. Хранить их вне проекта; в Git — только спецификацию и результаты без персональных данных.

### Карта покрытия (заполняется после получения)

Для каждого счёта-псевдонима и непрерывного диапазона записать: источник/локальный ID файла, SHA-256, заявленные и фактические from/to, время генерации и часовой пояс если указан, версия шаблона, присутствующие секции и уровни детализации, начальные/конечные cash и позиции, результат сверки, разрывы и причину ограничения. Не выводить период из имени файла или минимальной даты сделки: месяц без сделок тоже требует свидетельства покрытия.

Статусы покрытия: `unknown`, `gap`, `verified-period`, `verified-since-opening`, `opening-snapshot-only` — проектные метки Finly. Последний статус означает ограниченную историю, а не восстановление первоначальной себестоимости. Покрытие событий, остатков и ежедневных оценок фиксировать раздельно. Годовой NAV не доказывает наличие ежедневного ряда.

На 16 октября повторно проверены [Flex retention](https://www.ibkrguides.com/clientportal/performanceandstatements/flex.htm) и [Statement archive policy](https://www.ibkrguides.com/clientportal/performanceandstatements/statements.htm): четыре предыдущих года и текущий для Flex, 60 месяцев для monthly, пять предыдущих лет для annual. Ожидаемые окна в 2026 — Flex 2022–2026, annual 2021–2025; это вывод из политики, а не проверка конкретного счёта. Один ранний и один поздний файл не доказывают непрерывность: после проверки формата понадобится полный набор периодов от открытия либо подтверждённой стартовой даты.

## Соответствие существующей серверной модели

Проверены обе миграции в `supabase/migrations`, `src/domain/account.ts`, `src/domain/serverInput.ts` и `src/data/accountRepository.ts`.

| Уже существует | Ограничение для импорта | Решение первого импорта |
| --- | --- | --- |
| `portfolios` с owner и составной уникальностью `(user_id, id)` | Нет привязки к брокерскому счёту | Отдельная owner-scoped связь счёт → портфель; один счёт не импортировать повторно в другой портфель |
| `cash_entries`: только deposit/withdrawal, `source = manual`, положительный numeric | Нет сделок, выплат, ревизий, исходных строк; запрет отрицательного остатка не моделирует брокерский margin cash | Не использовать `add_cash_entry` для импорта; отдельные брокерские события и проводки после проверки mapping |
| `request_id` уникален у пользователя | Защищает повтор ручного RPC, а не перекрытие отчётов | Сохранить ручной механизм; в импорте нужны отдельные ключи пакета, подтверждения и событий |
| `import_batches`: owner, portfolio, path, hash, format, status | Только uploaded/review/applied/failed; нет staging, периода, версии, результата сверки | Расширить миграцией после образцов; не выдавать текущую таблицу за работающий pipeline |
| `unique(user_id, sha256)` | Повтор файла ловится лишь у одного пользователя; смена XML/перекрытие не ловятся | Сохранить как проверку байтов; другой портфель при том же hash — конфликт назначения, не новый импорт |
| numeric и RPC, возвращающие суммы как text | Валидатор ручной формы принимает только положительные суммы до 18+18 знаков | Отдельный signed-decimal контракт импорта; никакого Number, cents или молчаливого округления |
| RLS и запрет прямой записи клиентом | Service role обходит RLS | Сохранить закрытые записи; сервер сам проверяет owner всей цепочки, не доверяет user_id из payload |
| Приватный `ibkr-reports`, лимит 10 MiB, чтение своего пути | Клиентская загрузка/изменение/удаление не разрешены | Авторизованный серверный приём, неизменяемый объект под owner/batch; публичные URL не создавать |

Пакет/staging не участвует в текущих `cash_balances` и Activity. Для будущего применения понадобятся новые read RPC с десятичными строками и явным происхождением. Не складывать брокерский cash snapshot с рассчитанными потоками; снимок служит контрольным остатком. Если в выбранном портфеле уже есть ручные IBKR-пополнения, применение блокируется до явного сопоставления/исключения из совместной проекции. Ни совпадение суммы/даты, ни название портфеля не доказывают дубль. Исходные ручные записи сохраняются с аудитом.

## Pipeline и контракт предпросмотра

Названия сущностей и полей ниже — внутреннее предложение Finly; не схема IBKR и не готовая миграция.

1. **Приём.** Проверить JWT/owner, принадлежность портфеля, лимит 10 MiB до разбора, разрешённый формат по содержимому. SHA-256 считать на сервере по полученным байтам. Не принимать архивы и внешние URL. Хранить immutable source с owner/batch и hash. Storage и Postgres не образуют общую транзакцию: потерянные загрузки сверять/удалять отдельной задачей; пакет не считать загруженным до подтверждения объекта.
2. **Разбор в staging.** Запретить DTD, внешние сущности, сетевые обращения, XInclude и раскрытие сущностей; задать ограничения глубины, числа узлов/строк и времени обработки. Начальные проектные лимиты: глубина 32, 100 000 записей, 30 секунд; подтвердить на реальных файлах, превышение — понятная ошибка без частичного применения. XML ошибки сервиса, даже при HTTP 200, не является пустым отчётом. Multi-account файл на первом шаге направлять на review, не смешивать счета автоматически.
3. **Нормализация.** Каждая запись несёт ссылку на batch/секцию/строку или node index, вид события, account, source ID при наличии, исходный тип и точные строковые decimal. Отдельно даты сделки и расчёта, исходный timestamp/zone, instrument и единицы количества. Отсутствующее поле остаётся missing, а не 0. Внутренние строки/хэши нормализовать детерминированно с версией алгоритма; сохранять исходное представление для аудита.
4. **Валидация и сравнение.** Проверить структуру, обязательные поля по подтверждённому mapping, период/счёт, детализацию, корректные даты/числа, валюты, связи и поддержку типов. Отдельно сверить cash и positions. Пропущенная секция и пустая секция различаются; неизвестный финансовый тип блокирует применение. Не включать Orders/Summary/Closed Lots как дополнительные исполнения.
5. **Предпросмотр.** Показать счёт-псевдоним, портфель, фактический период, границу полноты, версии, число new/unchanged/revised/ambiguous/unsupported событий, суммы по валюте и виду, строки ошибок с безопасной ссылкой на источник, cash/position differences. На мобильном экране — краткий итог и страницы деталей. Никакого общего итога через несогласованный FX или доходности. Кнопка `Apply import` доступна только при отсутствии блокирующих ошибок.
6. **Подтверждение.** Сервер выдаёт preview ID/digest, связывающий owner, batch hash, portfolio/account mapping, parser/mapping versions, решения review и ревизию учёта. Применять разрешено только этот неизменившийся preview; подменённый/устаревший digest возвращает `PREVIEW_STALE`. Клиентский флаг «проверено» не является основанием записи.
7. **Атомарное применение.** В одной DB-транзакции заблокировать owner/account, повторно проверить права, digest, ревизию, ключи событий и покрытие; записать события/ревизии/проводки/аудит и `applied`. Ошибка откатывает всю финансовую запись. Повтор того же confirmation request ID и payload возвращает прежний результат; другой payload с тем же ID — конфликт. После сетевого timeout сначала получить статус прежнего batch/request, затем повторить тот же запрос, не новый импорт.

Расширение `import_batches`: requested/actual range, account mapping, generated/received timestamps, parser/mapping/canonicalization versions, preview digest, ledger revision, validation summary, confirmation request ID, applied_at и безопасный error code. Staging хранит исходные ссылки, нормализованные записи, кандидатов сопоставления и ошибки. Broker events хранят устойчивую identity, immutable revisions, связи replacement/cancellation и postings. Coverage и opening snapshots — отдельные сущности. Финальную SQL-схему выбрать после проверки cardinality и ID в образцах.

Состояния первой версии можно оставить совместимыми: `uploaded → review → applied`, технический отказ → `failed`. В `review` отдельно хранить `ready`/`blocked`, а не считать любой review готовым. Повтор разбора failed/review увеличивает версию попытки и инвалидирует preview; applied неизменяем, исправление — новый связанный пакет. Парсер новой версии может пересмотреть тот же исходный объект, не создавая вторую финансовую запись.

## Точность и сверка

- Денежные значения, quantity, price, multiplier, FX — decimal strings до PostgreSQL numeric; арифметика на сервере numeric или точным decimal-алгоритмом. JSON также содержит строки. Ограничения разрядности задаются явно после проверки образцов; превышение блокирует строку/пакет, не округляется. Дробные количества допустимы в модели.
- По каждой исходной валюте: начальный cash + подписанные денежные проводки = конечный cash на одной временной основе. Settled и trade-date cash сверять отдельно, учитывая незавершённые расчёты. Base-currency summary не добавлять как ещё одну валютную проводку. Отрицательный брокерский cash не объявлять ошибкой автоматически.
- По инструменту и единице: начальная позиция + изменения от executions/transfers/corporate actions = конечная позиция. Акции и номинал облигаций не взаимозаменяемы. Отдельно проверить multiplier, НКД, clean/dirty price и погашение.
- Net cash, commission, taxes и отдельные fee-секции сопоставить по образцам: расход учитывать один раз. Accrual не равен выплате; FX имеет две валютные стороны; дивиденд и withholding сохраняются раздельно. Не получать потоки из P/L колонок.
- По умолчанию разница должна быть точным нулём. Допуск возможен только для документированного округления конкретного контрольного поля; показать точную разницу, правило и единицу. Не скрывать расхождения общим epsilon. NAV использовать как брокерский контроль с датой и валютой, не как рассчитанную доходность.
- Начальный снимок с ненулевыми остатками — отдельный baseline, не фиктивный deposit/trade. Если происхождение/дата или снимок отсутствуют, история и итог остаются неподтверждёнными, применение блокируется до разрешения.

## Повторный импорт и исправления

| Ситуация | Действие |
| --- | --- |
| Тот же owner и hash файла | Вернуть прежний batch/status; несовпадающее назначение — конфликт |
| Пересекающийся период, подтверждённый одинаковый source ID и payload | Не создавать новое событие; добавить provenance из другого batch |
| Подтверждённый source ID, содержимое изменилось | Кандидат новой ревизии; показать diff и проверить правила корректировки, не суммировать обе версии |
| Нет устойчивого ID | Fingerprint — кандидат, не уникальный ключ; одинаковые строки требуют review с сохранением кратности |
| Два одинаковых реальных платежа | Сохранить оба при доказанной раздельности; без доказательства блокировать, не склеивать |
| Запись исчезла из нового отчёта | Не удалять; период/шаблон мог измениться |
| Явная отмена брокера | Связать с исходной записью и опубликовать проверенную ревизию/сторно; без исходника — review |
| Ручная корректировка/исключение импортированного события | Отдельный слой с причиной/аудитом; реимпорт не отменяет его молча, конфликт блокирует |
| CSV и Flex перекрываются | Выбрать подтверждённый источник диапазона либо явно сопоставить события; не складывать оба |
| Старый и новый account ID | Отдельные источники до подтверждённого сопоставления; перенос активов не превращать в покупку |

Предлагаемая область identity: owner + broker account + тип события + подтверждённый source ID (и дополнительный discriminator, если образцы показывают несколько строк на ID). Portfolio, batch hash, order ID или дата сами по себе не ключ события. Уникальные ограничения и блокировка транзакции нужны и при двух одновременных запросах; предварительного SELECT недостаточно.

## Ошибки и безопасность

| Код Finly (предложение) | Поведение |
| --- | --- |
| `INVALID_REPORT`, `LIMIT_EXCEEDED` | Остановить до staging/применения, объяснить формат/лимит |
| `ACCOUNT_MISMATCH`, `PERIOD_MISMATCH`, `MISSING_SECTION` | Review blocked; запросить правильную выгрузку/настройки |
| `UNSUPPORTED_EVENT`, `INVALID_DECIMAL`, `AMBIGUOUS_ID`, `RECONCILIATION_FAILED` | Review blocked с адресом записи и причиной; без пропуска строк |
| `PREVIEW_STALE`, `REVISION_CONFLICT`, `MANUAL_OVERLAP` | Новый preview/явное разрешение конфликта; без автоматической перезаписи |
| `UNAUTHORIZED`, `PORTFOLIO_UNAVAILABLE` | Отказ без раскрытия чужих batch/path/событий |
| `TEMPORARY_FAILURE`, неизвестный результат confirm | Ограниченный повтор с прежним ID, чтение статуса; не маркировать timeout как отсутствие записи |

Для новых таблиц — RLS и owner-связи через составные FK, отсутствие прямой клиентской записи, отзыв EXECUTE у PUBLIC/anon для привилегированных RPC, фиксированный search_path и явная проверка auth.uid(). Для worker/service role проверки owner обязательны отдельно. Объект Storage не перезаписывать; путь проверять сервером, исключить чтение чужого owner. Применить принцип [RLS Supabase](https://supabase.com/docs/guides/database/postgres/row-level-security); changelog endpoint при подготовке не ответил, перед реализацией повторить проверку актуальной документации.

Логи содержат batch ID, код ошибки и счётчики; не исходный XML, токен, банковские/личные сведения или полные URL с query. Предпросмотр и error details доступны только owner. Очистку отчётов/staging согласовать с возможностью аудита: applied provenance не удалять фоновым retry. До первой записи реальных данных нужен защищённый backup базы/Storage вне Git и проверка восстановления, как предусмотрено SUPABASE_SETUP.md.

## Порядок реализации и критерии выхода

1. **Образцы и mapping.** Заполнить карту покрытия и таблицу `section/path → meaning → type → required/optional → identity → sign/unit → evidence file`. Получить доказательство ID на перекрытии. Непроверенные типы отметить unsupported. Это текущая зависимость; вымышленные XML-атрибуты не фиксировать в коде.
2. **Чистый адаптер и preview.** Реализовать безопасный parser и точную нормализацию отдельно от Expo и SQL. Реальные обезличенные образцы держать вне Git; синтетические тесты маркировать как unit fixtures, не свидетельство формата. Сначала без записи в облако.
3. **Staging и серверный API.** После mapping подготовить миграцию и owner-scoped preview/confirm/status, протестировать локально. Проверить backup/restore перед реальным импортом. Доступ к приватному bucket и текущие manual RPC не расширять без необходимости.
4. **Применение и чтение.** Проверить atomicity, concurrency, повтор после timeout и согласование ручных записей. Добавить отдельное отображение источника/периода и новых событий; не включать доходность. Только после этого подключать подтверждённые остатки к Overview.
5. **Автоматизация позднее.** После ручной приёмки повторно проверить Flex v3 API, секретное хранение, очередь, retry и ежедневное расписание. CSV-архивы подключать отдельным адаптером с теми же проверками; ранее недоступные периоды остаются gaps.

Обязательная матрица проверок для реализации:

- Байтовый повтор, перекрытие, перестановка строк/атрибутов, изменение шаблона, одна исправленная запись, исчезнувшая запись, два одинаковых платежа, CSV/Flex overlap.
- Высокая точность и очень малые значения, отрицательный cash, дробные quantity, комиссия в другой валюте, FX, налог/дивиденд, начисление/выплата; облигации и corporate actions только с подтверждённой семантикой.
- Некорректный/обрезанный XML, DTD/XXE/entity expansion, слишком большой/глубокий файл, XML ошибки сервиса, пустая/отсутствующая секция, неизвестный тип, multi-account, неправильный период и разрыв истории.
- Сбой между Storage и DB, сбой внутри apply (ноль частичных проводок), два конкурентных apply, потерянный ответ после commit, смена parser version/ledger revision после preview.
- Два настоящих Auth JWT: чужие portfolio/batch/event/path, подмена owner и preview, прямые INSERT/UPDATE/DELETE, anon, чтение numeric без строкового RPC. Локальный SQL SET ROLE не заменяет REST-проверку JWT и Storage.
- До/после любого blocked/failed пакета прежние опубликованные балансы неизменны. Preview не меняет ledger. Сверка полного применённого пакета сходится по валютам/инструментам, нет дублирования manual/import.

На данном подготовительном этапе изменена только документация. Парсер, миграции, UI импорта и подключение брокера не реализованы; SDK 57 API не менялись. Следующий практический шаг — получить минимальные обезличенные образцы и заполнить mapping, затем реализовать read-only preview.
